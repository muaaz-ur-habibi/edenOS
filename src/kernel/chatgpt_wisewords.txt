You do **not** need a bootloader to implement FAT12 support in your hobby OS.

Most tutorials mix together:

1. **Boot process**
2. **Filesystem implementation**
3. **Kernel loading**

…which makes it look like FAT12 *requires* a boot sector bootloader. It doesn’t.

The first 512 bytes on a FAT12 volume are simply:

* a **boot sector**
* containing:

  * BIOS Parameter Block (BPB)
  * optional boot code

The boot code can be garbage, empty, or unused if you are not booting from it.

---

# What you should do instead

Treat FAT12 as just a **disk format**.

You can:

* create a FAT12 floppy image
* put files inside it
* load the image in QEMU/Bochs
* have your existing loader/kernel read the FAT structures

without ever executing the FAT boot sector.

---

# Recommended setup

## Option 1 (best): separate bootloader and FAT image

This is the cleanest architecture.

```text
[ bootloader ] -> loads kernel
                    |
                    v
             kernel mounts FAT12 image
```

Example:

* stage1 bootloader (or GRUB)
* kernel binary
* FAT12 floppy image used as storage

This is how real systems work.

You can use GRUB for now and focus entirely on filesystem code.

Example QEMU:

```bash
qemu-system-i386 \
  -kernel kernel.elf \
  -fda fat12.img
```

or:

```bash
qemu-system-i386 \
  -drive file=fat12.img,format=raw
```

---

# Creating a FAT12 image without bootloader code

You can make a valid FAT12 image with standard tools.

Linux:

```bash
dd if=/dev/zero of=fat12.img bs=512 count=2880
mkfs.fat -F 12 fat12.img
```

This creates:

* boot sector
* FAT tables
* root directory
* data area

The boot sector contains default boot code you can ignore.

Then copy files into it:

```bash
mcopy -i fat12.img myfile.txt ::
```

or mount it:

```bash
mkdir mnt
sudo mount -o loop fat12.img mnt
```

# What your OS needs to implement

Your FAT12 driver only needs to understand:

## 1. BPB (BIOS Parameter Block)

Located in sector 0.

Important fields:

```c
bytes_per_sector
sectors_per_cluster
reserved_sectors
fat_count
root_entries
sectors_per_fat
```

These let you compute filesystem layout.

---

# FAT12 layout

```text
Sector 0:
    Boot sector + BPB

Next:
    FAT #1

Next:
    FAT #2

Next:
    Root directory

Next:
    Data region (clusters)
```

---

# Core formulas

Root directory size:

```c
root_dir_sectors =
    ((root_entries * 32) + (bytes_per_sector - 1))
    / bytes_per_sector;
```

First data sector:

```c
first_data_sector =
    reserved_sectors +
    (fat_count * sectors_per_fat) +
    root_dir_sectors;
```

Cluster → sector:

```c
first_sector_of_cluster =
    ((cluster - 2) * sectors_per_cluster)
    + first_data_sector;
```

---

# The only “hard” part: FAT12 entries

FAT12 uses **12-bit entries**.

Two cluster entries are packed into 3 bytes.

Example:

```text
byte0 byte1 byte2

cluster n     = low 12 bits
cluster n +1  = high 12 bits
```

Reading cluster chain:

```c
fat_offset = cluster + (cluster / 2);
```

Then extract differently for odd/even clusters.

This is the trickiest part of FAT12.

# Important realization

The “boot sector” is BOTH:

* executable code area
* filesystem metadata area

Your OS only cares about the metadata.

So you can completely ignore the executable part.

---

# Strong recommendation

Do **not** write your own bootloader yet.

Use:

* GRUB
* Limine
* existing stage1 loader

and focus on:

* memory management
* VFS
* FAT12 parsing
* ELF loading
* scheduler

Filesystem development is much easier when booting is already solved.

---

# Useful strategy for testing

Generate known FAT12 images and inspect them with tools.

Very useful:

* `mdir`
* `mcopy`
* `hexdump`
* `xxd`

Example:

```bash
xxd fat12.img | less
```

You’ll quickly understand FAT layout visually.

---

# A better long-term idea

FAT12 is historically useful, but FAT16 or FAT32 is easier to scale and more practical later.

Still, FAT12 is excellent for learning because:

* tiny
* simple
* fixed root dir
* easy cluster math

So it’s a good starting point.
